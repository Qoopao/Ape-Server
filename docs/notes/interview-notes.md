## 0. 答题总纲（先记住这个框架）

### 0.1 三段式

```
1) 约束：这个场景的硬指标是什么（延迟？吞吐？一致性？开发速度？）
2) 候选：同类组件至少说 3 个，说清各自的"决定性差异"
3) 代价：我选的那个，牺牲了什么，我怎么补的
```

**只说 1 和 2 的人很多，能说 3 的才像做过。** 因为任何选型都是"用某个劣势换某个优势"，说不出劣势就说明没真正用过。

### 0.2 三句万能句式

| 场景 | 句式 |
|---|---|
| 被问"为什么用 X" | "在这个场景下我的硬约束是 A，X 的优势正好是 A；我放弃了 B 方向的优势，因为当前瓶颈不在那里。" |
| 被问"为什么不用 Y" | "Y 更适合 Z 场景；我这里是 A 场景，用 Y 要多付 M 成本，收益在 N 之后才出现，所以现在没做。" |
| 被追问"以后扩展怎么办" | "瓶颈会先出现在 P，那时我会做 Q；接口已经按 Q 的形状留好了（举一个具体例子）。" |

### 0.3 一条重要纪律

**不要背组件名列表，要讲"如果我换成另一个会怎样"。** 面试官听到"我对比过 brpc 和 gRPC，brpc 的 bthread 在高并发下更稳，但我们没有成熟的 C++ 服务发现，gRPC 的反射和拦截器能直接接 OTel"，会立刻判断你是真选过。

## 1. 项目的硬约束（一切都从这里推导）

| 约束 | 具体内容 | 对选型的影响 |
|---|---|---|
| 语言诉求 | 想练 C++ 现代特性（C++20 协程、零 GC、手动内存/生命周期） | 直接排除了 Go/Java，也决定了后面所有库都得是 C++ 生态 |
| 部署条件 | 单机开发（一台机器跑全部依赖） | 中间件选"能 docker 一键起"的；不引入 K8s 依赖 |
| 性能目标 | 长连接 1–5 万、单聊在线 P99 < 200ms | 需要无 GC 停顿、需要可控的线程/IO 模型 |
| 可观测 | 要能定位"这条消息卡在哪一段" | 选 OTel 全链路，而不是只接 Prometheus |
| 团队规模 | 一人全栈 | 组件要"少而通用"，宁可自己写薄封装（BackbonService），也不引入需要专人运维的组件 |
| 客户端诉求 | 桌面端、要和 C++ 服务端同栈、包体要小 | Qt6 Widgets，而不是 Electron |

**面试讲法**：

> "这个项目的约束不是'要扛百万并发'，而是'一个人在一台机器上，把一条完整的 IM 链路做对，并且能观测、能扩'。所以我的选型原则是：**组件数量少、每层只选一个、优先选能解释清楚的**。比如我没上分库分表，因为我的瓶颈还没到那；但我把 outbox 和 ACK 回执做对了，因为那是逻辑正确性问题，早做晚做都得做。"

## 2. 技术选型逐项（弹药库）

每一项给三块：**候选对比表 → 决策与理由 → 代价与追问**。

### 2.1 语言与标准：C++20

| 维度 | C++20 | Go | Java 21 | Rust |
|---|---|---|---|---|
| 运行时 | 无 GC，确定性延迟 | GC，STW 亚毫秒~毫秒 | JIT 需预热，GC 可调 | 无 GC |
| 长连接内存/连接 | 最低（可压到几十 KB） | 中（goroutine 2KB 起，调度器开销） | 高 | 低 |
| 开发效率 | 低（编译慢、生命周期、模板报错） | **最高**（goroutine + channel 开箱） | 高（生态最全） | 中（borrow checker 曲线） |
| IM 生态 | 少（多数要自己攒） | 中（有大量开源网关） | **最全**（Netty、OpenIM 参考实现多） | 少 |
| 协程/并发原语 | C++20 coroutine（无运行时，需自己管生命周期） | goroutine（最省心） | 虚拟线程（21+） | async/await |

**决策**：C++20。

**真实理由**（面试要说实话，才有说服力）：

> "选 C++ 有两个原因。一是我的目标就是练 C++ 的网络编程和协程，选 Go 就绕过了我想练的东西。二是工程上它确实成立：IM 网关是典型的'大量长连接 + 低延迟转发'，无 GC 意味着没有 STW 抖动，内存占用也更可控。"

**代价**（必须主动说）：

> "代价是开发效率大概低 2–3 倍，而且很多轮子要自己写：协程的异常/生命周期、连接管理、甚至服务注册都要自己封一层。生产上如果团队以交付速度为先，我会推荐 Go。"

### 2.2 构建与依赖：CMake + vcpkg

| 方案 | 优势 | 劣势 | 适合 |
|---|---|---|---|
| **CMake + vcpkg** | 事实标准；vcpkg 免手工编依赖；triplet 可交叉 | vcpkg 首次编译极慢；版本锁定要靠 manifest | 通用 C++ 项目 |
| Conan | 更严格的依赖图、二进制缓存强 | 学习曲线、包质量参差 | 大型多团队 |
| Bazel | 增量构建最快、可重现性最好 | 生态偏 Google、C++ 规则陡 | 超大型单体仓库 |
| Makefile/手写 | 零依赖 | 不可维护 | 玩具项目 |

**决策**：CMake + vcpkg（`x64-linux` 服务端、`x64-windows` 客户端）。

**代价**：vcpkg 编译一次几分钟到十几分钟；Windows 侧要为 WCDB 写自定义 port（实际踩过：需要两个 patch 才能编过 DLL 导出）。**面试可讲**："依赖管理是我这个项目最脏的一块，我在客户端为 WCDB 维护了一个 vcpkg port，带两个 patch。"

### 2.3 网络库：Boost.Asio + Beast

| 方案 | 模型 | TLS/WS | 性能 | 成本 |
|---|---|---|---|---|
| **Asio + Beast** | Proactor + 协程（`awaitable`） | 都内置 | 中上 | 模板重、编译慢、报错长 |
| uWebSockets | Proactor，极致优化 | 内置 | **最高** | API 简化、生态小、调试难 |
| libwebsockets | C 回调 | 内置 | 中 | 回调风格、状态机膨胀 |
| muduo | Reactor（one loop per thread） | **需自己实现 WS 握手** | 中 | 学习型，功能少 |
| 直接用 OpenSSL + 手写帧 | 完全可控 | 自己写 | 看你写多好 | 极高 |

**决策**：Beast（Asio 上的 WebSocket 实现）。

**理由**：

> "我要的是一个库同时给我 TLS、WebSocket、协程三件事，Beast 是唯一同时满足的。uWebSockets 性能更好，但它的 API 把很多控制权拿走了，我这种要精细控制写队列、要自己实现离线补投的场景反而不好用。"

**代价**：

> "模板导致编译慢、报错极长；而且 Beast 的写操作有 soft_mutex，多协程并发写会断言失败——这就是我后来为什么要自己做一个'每连接一个写队列'的原因。"

**面试钩子**：这段能自然引出你做的 `write_queue_`（`asio::experimental::channel` 串行化写），是个很硬的实现细节。

### 2.4 并发模型：协程 + strand + IOC_Pool

| 模型 | 写法 | 万连接下 | 风险 |
|---|---|---|---|
| 回调（状态机） | 分散、易漏 | 可行 | 可读性差 |
| one loop per thread + 阻塞 IO | 简单 | **不行**（线程数爆炸） | 阻塞一个就卡一片 |
| 线程池 + 阻塞 | 简单 | 不行 | 同上 |
| actor 框架 | 需引框架 | 可行 | 依赖重 |
| **C++20 协程 + strand + IOC_Pool** | 顺序化、同步写法 | **可行** | 生命周期、异常、调试 |

**决策**：每连接绑定一个 strand（连接内无锁），业务跑在 `IOC_Pool`（4 个 io_context × 1 线程），accept 单独一个线程。

**理由（可以讲得很细，这是加分项）**：

> "多线程 run 同一个 io_context 会有惊群和锁竞争，所以我用的是 IOC_Pool 模型：N 个 io_context，每个一个线程，连接进来时 round-robin 分配到某个 ioc 的 strand。因为一条连接的所有读写都在同一个 strand 上，连接内部状态完全不用加锁；跨连接共享的只有那张 session 表，用 shared_mutex。"

**代价**：

> "协程的生命周期要自己保证——比如 `co_spawn(..., detached)` 会把异常吞掉，不写 catch 你连日志都没有。我被这个坑过，后来在协程入口统一兜 catch。"

### 2.5 RPC：gRPC

| 方案 | 性能 | 多语言 | 流式 | C++ 异步体验 | 生态 |
|---|---|---|---|---|---|
| **gRPC** | 中（HTTP/2 头开销） | **最好** | 支持 | 差（CQ / Reactor，回调地狱） | 最好（拦截器、反射、OTel） |
| brpc | **最高**（bthread） | 弱（主要 C++） | 部分 | 好（同步写法异步执行） | 中（百度系） |
| Thrift | 中 | 中 | 否 | 一般 | 衰退 |
| 自研二进制 | 最高 | 无 | 自己写 | 自己写 | 无 |

**决策**：gRPC。

**理由**：

> "我需要三样东西：protobuf 原生、拦截器（接 OTel trace）、以及未来客户端可能换语言时的兼容性。brpc 单机性能更好，但它的多语言和生态弱，而且我不想自己写服务发现。"

**代价**：

> "C++ 的异步 API 很难用。我用的是 CallbackServerContext + DefaultReactor + 协程：handler 里 `co_spawn` 一个协程，结束前调 `reactor->Finish()`。这是整个项目里最不优雅的一块。"

**面试钩子**：这段引出 `BaseServiceServer` 模板封装 —— 9 个服务共用同一套启动/注册/等待就绪逻辑。

### 2.6 序列化：Protobuf（+ 业务正文用 JSON）

| 方案 | 体积 | 解析速度 | Schema | 零拷贝 | 生态 |
|---|---|---|---|---|---|
| **Protobuf** | 小 | 快 | 有（强类型 + 兼容规则） | 否 | 最好 |
| FlatBuffers | 小 | **免反序列化** | 有 | 是 | 中（游戏/移动） |
| Cap'n Proto | 小 | 免反序列化 | 有 | 是 | 小 |
| JSON | 大 | 慢 | 无 | 否 | 最好 |
| MessagePack | 中 | 快 | 无 | 否 | 中 |

**决策**：**外层信封与所有 RPC 用 protobuf；消息正文 `content` 用 JSON 字节**。

**理由**：

> "信封必须强类型且能演进，所以用 protobuf；但消息正文是业务内容，客户端类型多、字段常变，用 JSON 更灵活——服务端只做透传和一段预览截断，不需要理解正文结构。"

**代价**：

> "代价是正文没法在服务端做结构化查询（比如按消息内容搜索）；如果要做全文检索，得再接 ES 或把正文也 schema 化。"

### 2.7 关系库：MySQL 8.4

| 维度 | **MySQL 8.4** | PostgreSQL 16 |
|---|---|---|
| 团队/运维熟悉度 | 高（教程、DBA 多） | 中 |
| JSON 能力 | 一般（JSON 函数弱于 PG） | **强（JSONB + GIN 索引）** |
| 复杂查询/窗口函数 | 8.0+ 已支持 | 更强 |
| 复制/高可用 | 成熟（主从、组复制） | 成熟（流复制、逻辑复制） |
| 自增/序列 | 简单 | 序列更规范 |
| 我需要的 | 事务、行锁（`FOR UPDATE`）、唯一键、`INSERT ... ON DUPLICATE KEY UPDATE` | 同样有 |

**决策**：MySQL。

**理由**："我的核心需求是**事务 + 行锁 + 唯一键做幂等**（outbox 的 `dedupe_key`、会话的 `GREATEST` 更新、群 seq 的行锁分配），这些 MySQL 都成熟；JSON 我只用来存会话摘要，不需要 PG 的 JSONB 索引。"

**代价**："复杂分析查询会难受（如果以后做运营报表，可能要接 ClickHouse/PG 只读库）。"

### 2.8 缓存：Redis 7.2

| 方案 | 数据结构 | 持久化 | 多线程 | 典型用途 |
|---|---|---|---|---|
| **Redis** | 最丰富（String/Hash/ZSet/Stream/Lua） | RDB+AOF | 命令单线程（6.0+ IO 多线程） | 缓存、路由、限流、分布式锁 |
| Memcached | 纯 KV | 无 | 多线程 | 纯缓存（大对象） |
| 本地 LRU（自研/folly） | KV | 无 | 是 | 超热数据，纳秒级 |
| etcd | KV + watch | Raft | — | 配置/注册，不适合当缓存 |

**决策**：Redis。

**理由**："我不只要 KV，还要 **TTL（在线状态/路由自愈）、Lua（路由 CAS 续期）、ZSet（未来的延迟任务）**，这三样只有 Redis 有。"

**代价与教训**（这是我项目里最值钱的复盘素材之一）：

> "代价是网络往返，所以它只该做'提示'不该做'判据'。我踩过的坑正是把 Redis 的在线状态当成了投递闸门——写失败就等于用户被判离线，消息被确认成已分发，然后就丢了。后来我把判据改成目标网关的返回值，Redis 只留作路由。"

### 2.9 消息正文存储：MongoDB

| 方案 | 写入 | 按会话范围查 | 分片 | 事务 | 运维 |
|---|---|---|---|---|---|
| **MongoDB** | 快 | **天然（`{convID, seq}` 复合索引）** | 分片键可选 convID | 单文档原子，跨文档弱 | 中 |
| MySQL 大表 | 中 | 需分库分表后才快 | 手工 | 强 | 中（但分表复杂） |
| Cassandra / ScyllaDB | **极快** | 按分区顺序读最优 | 天然 | 轻量事务 | 重 |
| 对象存储（S3） | 慢 | 不支持 | — | 无 | 低（但功能不够） |

**决策**：MongoDB（库 `IM-System`，集合 `msg`）。

**理由**：

> "消息是'只追加、按会话 + 序号范围读'的访问模式。Mongo 的 `{convID, seq}`、`{recvID, seq}` 复合索引正好覆盖这两种查询，而且我不需要跨文档事务——幂等靠 `{serverMsgID}` 唯一索引 + `$setOnInsert` 就够了。"

**代价**：

> "跨文档事务弱，所以'写消息 + 更新会话'不能放一个事务里，这才有了 outbox 两阶段；另外大盘数据要自己做归档（我目前没做 TTL，是个已知缺口）。"

**面试钩子**：这里自然引出 outbox —— 你不是"为了用而用"，是被存储的约束逼出来的。

### 2.10 消息队列：Kafka

| 方案 | 吞吐 | 顺序 | 堆积能力 | 延迟 | 运维 |
|---|---|---|---|---|---|
| **Kafka** | **最高** | 分区内有序 | 强（磁盘） | 毫秒级 | 中（KRaft 后免 ZK） |
| Pulsar | 高 | 分区有序 | 强（存算分离） | 更低 | 复杂 |
| RabbitMQ | 中低 | 队列有序 | 弱 | 微秒级 | 中 |
| Redis Streams | 中 | 有序 | 弱（内存） | 低 | 低 |
| NATS JetStream | 高 | 有序 | 中 | 低 | 低 |

**决策**：Kafka（topic `msg_topic`，10 分区，key=conversationID）。

**理由**：

> "我要的是'同一会话的消息严格按序进消费者'，所以用 key 做分区——同一个 convID 永远落同一分区，消费端按 (topic, partition) 的 lane 串行处理，就能保证会话内有序。RabbitMQ 低延迟但堆积弱，我这边离线用户可能积压很多，需要强堆积。"

**代价**："延迟是毫秒级，所以在线推送链路里 Kafka 不是唯一路径——真正的低延迟部分是网关直推。"

### 2.11 服务发现：etcd

| 方案 | 一致性 | watch | 健康检查 | 依赖 | 备注 |
|---|---|---|---|---|---|
| **etcd** | Raft（CP） | 原生 watch | **需自己做**（lease + KeepAlive） | 轻 | K8s 同源 |
| Consul | Raft | 有 | **内置强** | 中 | 多数据中心 |
| ZooKeeper | ZAB | 有（一次性） | 会话 | 重 | 老牌，客户端难用 |
| Nacos | Raft/Distro | 有 | 内置 | 中 | Java 生态 |
| K8s Service | — | — | 内置 | 需 K8s | 无 SDK 依赖 |

**决策**：etcd + 自己封一层 `BackbonService`。

**理由**：

> "etcd 轻、有 lease 和 watch，且我的可观测/部署栈本来就在容器里。但它没有内置健康检查，所以注册/心跳/注销这套协议要自己写——这就是 BackbonService 存在的原因：把'服务注册 + 方法级元数据 + 在线状态查询'收成一个内部网关，业务服务只调它，不直接碰 etcd 客户端。"

**代价**："BackbonService 本身成了单点（如果它挂了，新注册失败，但已有注册因为 lease 还在所以仍可用）。这是一处已知的架构债。"

### 2.12 可观测：OpenTelemetry

| 方案 | Trace | Metric | Log | 厂商锁定 | 接入成本 |
|---|---|---|---|---|---|
| **OTel SDK + Collector** | 有 | 有 | 有 | **无**（可换后端） | 中（要接 sink、拦截器） |
| Prometheus + Jaeger 直连 | 有 | 有 | 无（另接 Loki） | 低 | 低（但聚合靠自己） |
| SkyWalking | 有 | 有 | 有 | 中 | Java 生态强，C++ 弱 |
| 自研埋点 | 有 | 有 | 有 | 高 | 高 |

**决策**：OTel 全链路（trace + metric + log），Collector 分发到 Jaeger / VictoriaMetrics / Elasticsearch+Kibana。

**理由**：

> "我要用一个 ID 把'网关 → MsgService → outbox → Kafka → PushService → 网关'串起来。OTel 的 traceparent 能穿透 gRPC metadata 和 Kafka 消息头，这一条是它相对 Prometheus+Jaeger 直连的决定性优势。"

**代价**："多一跳 Collector，链路长、配置多；SDK 的 C++ 部分文档少，我花了比较多时间在 exporter 和 interceptor 上。"

### 2.13 ID 生成：三种 ID，三种用途（这题很能体现思考）

| 方案 | 有序性 | 唯一性保证 | 索引友好 | 依赖 |
|---|---|---|---|---|
| Snowflake | **时间有序** | worker/datacenter + 时钟 | 好（递增） | 需分配 worker id |
| UUID v4 | 无序 | 概率唯一 | **差**（B+树随机插入） | 无 |
| DB 自增 | 有序 | 库内唯一 | 好 | 单库瓶颈 |
| Redis INCR | 有序 | 单实例 | 好 | Redis |
| 号段（Leaf） | 有序 | 号段服务 | 好 | 号段表 |

**决策（三套并存，各有理由）**：

| ID | 用什么 | 为什么 |
|---|---|---|
| `serverMsgID`（消息唯一标识） | **UUID v4** | 不需要有序，只需要全局唯一 + 无协调；它同时是 Mongo 的唯一索引，用 UUID 可以做到"客户端重试时天然幂等"（`$setOnInsert`） |
| `seq`（会话内序号） | 单聊 **Snowflake**、群聊 **`last_seq + 1`** | 见下方专门解释 |
| `account`（用户账号） | **号段池**（`account_pool` 预生成 10 位号 + `FOR UPDATE` 取号） | 账号要好看、不可预测、且注册是低频操作，号段池最合适 |

**为什么单聊 seq 用 Snowflake、群聊用自增？**（高频追问）

> "因为两者对 seq 的要求不同：单聊我需要**跨会话全局有序**——会话列表要按时间排序、分页要能用 seq 做游标，Snowflake 天然满足；群聊我需要**会话内连续**——客户端要检测'我有没有漏掉某条'，seq 必须无空洞，所以群内用 `last_seq + 1` 在行锁里分配。
> 代价是套了两套语义：单聊的 seq 有洞（不能用来检测丢消息），所以单聊的缺口检测靠 receipts 回执而不是 seq。这是我特意接受的复杂度。"

### 2.14 认证：UUID token + Redis

| 方案 | 无状态 | 可吊销 | 每次校验成本 | 适合 |
|---|---|---|---|---|
| **UUID token + Redis** | 否 | **是** | 一次 Redis 查询（仅登录时） | 需要踢下线 |
| JWT | **是** | 难（要黑名单） | 验签（本地） | 微服务横向扩展 |
| Session（服务端内存） | 否 | 是 | 无 | 单机 |
| OAuth2 | 是 | 是 | 重 | 第三方登录 |

**决策**：UUID + Redis（`token:{uuid}` → `{userID,account}`，TTL 7 天）。

**理由**："IM 必须能踢人（改密码、异地登录、风控），JWT 做不到即时吊销，除非再维护黑名单——那还不如直接用 Redis。代价是每次登录多一次 Redis 查询，但这个操作只在建立连接时发生一次，可接受。"

### 2.15 客户端：Qt6 Widgets + WCDB

| 框架 | 语言 | 包体 | 内存 | UI 开发速度 | 跨端 |
|---|---|---|---|---|---|
| **Qt6 Widgets** | C++ | 小（20–40MB） | 低 | 慢（手写 .ui + 自绘样式） | Win/Linux/Mac |
| Electron | JS/TS | **大（100MB+）** | 高（多进程 Chromium） | **快** | 全平台 |
| Flutter | Dart | 中 | 中 | 中 | 全平台（桌面成熟度一般） |
| WPF | C# | 小 | 中 | 中 | 仅 Windows |

| 本地库 | 加密 | ORM | Windows 支持 | 生态 |
|---|---|---|---|---|
| **WCDB** | 内置 SQLCipher | 有（对象映射） | 需自建 vcpkg port | 移动端为主 |
| 裸 SQLite | 需自己接 SQLCipher | 无 | 好 | 广 |
| Realm | 有 | 有 | 一般 | 中 |
| LevelDB | 无 | KV | 好 | 广 |

**决策**：Qt6 Widgets + WCDB。

**理由**："和服务端同栈（C++），包体小、内存低，符合桌面 IM 的形态；WCDB 自带 ORM 和加密，省掉自己写 DAO 和接 SQLCipher 的活。"

**代价（诚实说，这是加分点）**："Qt 的 UI 开发效率确实低，很多控件样式要自绘；WCDB 在 Windows 下没有现成 vcpkg port，我自己写了带两个 patch 的 port 才编过。如果重来、且 UI 复杂度更高，我会考虑 Flutter。"

## 3. 架构思路与关键取舍

### 3.1 一张图讲清分层

```
客户端 ──WSS──▶ 网关（有状态：连接表 + 写队列）
                    │  gRPC（无状态）
                    ▼
    ┌───────────┬───────────┬──────────────┐
    │ Auth      │ 社交域     │ 消息域        │
    │ 注册/登录 │ 好友/群/会话│ Msg / Push    │
    └───────────┴───────────┴──────────────┘
                    │
      ┌─────────────┼──────────────┬─────────────┐
      ▼             ▼              ▼             ▼
    MySQL         MongoDB        Redis          Kafka
  （关系/状态）  （消息正文）  （路由/缓存/令牌）（异步投递）
```

**一句话概括架构**：

> "**网关有状态、服务全无状态、存储按访问模式拆分、异步用 outbox 兜住。**"

### 3.2 为什么网关必须有状态，而其他服务必须无状态

| 组件 | 是否有状态 | 为什么 |
|---|---|---|
| 网关 | **有**（连接表：account → session） | WebSocket 是长连接，socket 对象只能存在于持有它的进程里，这无法外部化 |
| Auth / Msg / Push / Group / Friend / Conversation | 无 | 无状态才能随意扩副本、随意重启 |
| `GatewayPushService` | 无（只是网关进程的一个 RPC 入口） | 它自己不存状态，状态在网关的 `WSSessionManager` 里 |

**追问："既然网关有状态，还能水平扩吗？"**

> "能，但要解决'推给某个用户时，怎么找到他所在的网关'。这就是我后来加的 `gw:user:{account}` 路由表 + 广播兜底：路由表只影响性能，正确性由网关的返回值保证。"

### 3.3 消息可靠性的三段式（核心叙事）

```
① 受理：客户端发 → 网关 → MsgService → 写 im_outbox（返回 PENDING 或直接成功）
② 落库：OutboxWorker 取任务 → Mongo 存正文 + MySQL 更新会话 → stage=1
③ 投递：发布到 Kafka → PushService 消费 → 查网关 → 推送 → 等客户端 ACK → receipts
```

**为什么要有 outbox？**

> "因为'写数据库'和'发消息到 MQ'没法放进一个事务。outbox 把'要发的消息'也变成数据库里的一行，跟业务数据同事务提交；再由 worker 把这一行搬去 MQ。这样即使进程在提交后立刻挂了，重启后 worker 还会捡起来。这是**事务性发件箱（transactional outbox）**模式。"

**为什么要有 receipts（持久 ACK 回执）？**

> "因为'网关接受' ≠ '客户端收到'。真正的送达凭据是客户端回的 ACK，我把它落成 MySQL 的一行（`im_message_receipts`，主键 `(owner, serverMsgID)`）。**没回执就算没送到**，下次登录继续补。"

**为什么不用 Redis 记 ACK？**

> "Redis 是缓存，会过期、会丢；'是否送达'是正确性问题。我一开始确实想用 Redis 的 pending 集合，后来改成 MySQL 持久回执，因为进程重启后还能查得到。"

### 3.4 双轨消息模型（最容易被追问的点）

| | 单聊 | 群聊 |
|---|---|---|
| 正文存储 | MongoDB | MySQL `im_group_messages` |
| seq 生成 | Snowflake（全局有序、会话内不连续） | `last_seq + 1`（会话内连续） |
| 投递 | Kafka → PushService → 网关 | GroupService 自己的 2s 轮询 + `Notice` |
| 离线恢复 | 按会话 cursor 补投 | 客户端 `Pull` |

**为什么群聊不共用单聊的 Kafka 链路？**

> "三个原因。一是**扇出模式不同**：单聊是 1 对 1，PushService 拿到一条消息查一次在线就够了；群聊是 1 对 N，200 人群就是 200 次推送，走 Kafka 反而放大。二是**seq 语义不同**：群聊需要会话内连续（客户端要补洞），所以必须用行锁分配 `last_seq+1`，这跟 Snowflake 的全局有序是冲突的。三是**离线恢复方式不同**：群消息量大，不适合登录时全推，客户端按 `lastSeq` 自己 Pull 更合适。"

**追问："两套模型不觉得重复吗？"**

> "重复是有意付的代价。共用一套我要么放弃单聊的全局有序，要么放弃群聊的连续序号；这两个都是客户端强依赖的语义。我选择在两套模型之上统一'客户端看起来的接口'——都是 `type 200/251` 推下来、都按 seq 排序，用户感知不到差异。"

### 3.5 关键取舍清单

| 取舍点 | 我的选择 | 备选 | 我付的代价 |
|---|---|---|---|
| 一致性 vs 可用性 | **最终一致**（消息可能延迟，但不会丢） | 强一致（两阶段提交，延迟高） | 需要补投、需要幂等 |
| 网关有状态 vs 无状态 | 有状态 + 路由表 | 无状态（连接信息放 Redis） | 路由与互踢问题 |
| 单进程 vs 多进程 | 先单进程跑通，再拆 | 一开始就拆 | 出现过"直调内存"的耦合债 |
| 群聊共用 vs 独立 | 独立链路 | 复用单聊 | 两套代码、两套监控 |
| 全量补投 vs 按会话 | **按会话有界快照** | 全量补投（简单但 O(全部历史)） | 客户端要自己拉历史 |
| 是否上分库分表 | **不上** | 提前分片 | 单表上限（当前量级不需要） |

### 3.6 我的瓶颈在哪里（主动说，别等问）

| 阶段 | 先撞到的墙 | 对策 |
|---|---|---|
| 1 万连接 | 单进程文件描述符 / 内存 | 调 ulimit、连接对象瘦身 |
| 5 万连接 | 单个 io_context 线程的 CPU | IOC_Pool 多 worker（已做） |
| 更多 | **单网关容量**（进程内存表 + CPU） | 已实现 PR-1～6、PR-8：多网关 + 路由表 + 广播兜底；剩余 PR-7（客户端重连） |
| 消息量 | MySQL 写放大（会话表双行更新） | 批量更新、按会话分片 |
| 存储量 | Mongo 无 TTL、单集合膨胀 | 归档/分片（未做） |

## 4. 我是如何改进与复盘的

### 4.1 我的复盘方法论（四步，可复用）

```
1) 现象：用户能看到什么（不是"报错了"，而是"用户收不到消息"）
2) 根因：追到"哪个判据/哪个时序"错了，而不是"哪个函数写错了"
3) 不变量：这次修复后，什么样的错误从此不可能发生（写成一条约束）
4) 验证：怎么证明它真的不会了（可执行的验收，而不是"我觉得好了"）
```

**为什么强调第 3 步**：修 bug 只解决一次，**沉淀成不变量才能防一类**。我项目里最后留下 6 条不变量（见 4.4），就是这轮复盘的产物。

### 4.2 案例 A：把 Redis 当投递闸门 → 在线用户丢消息

| 阶段 | 内容 |
|---|---|
| **现象** | 用户明明在线，发消息收不到；重登后消息才到 |
| **初判** | 以为是 Kafka 丢消息 |
| **真因** | PushService 先查 `user:{id}:online`，值为空/`"0"` 就直接跳过推送；而这个 key 有 4 个写者（登录、心跳、断线、Backbon 负缓存），写失败/竞态/负缓存都会让它错。跳过之后 `ConfirmMessageDispatch` 照样把 outbox 置成"已分发"，于是不再重试 |
| **修法** | 删掉闸门：**总是**调网关的 `PushFrame`，用它的返回值（唯一权威）判断在线；Redis 改为只做路由 |
| **沉淀** | **判据必须来自权威源**。缓存可以加速，但不能否决。 |
| **追问准备** | "为什么不能把 Redis 写可靠一点？"→ 因为缓存和数据库之间永远有窗口，你要么做一致性协议（成本远高于收益），要么别让它参与决策。 |

### 4.3 案例 B：三处"直调内存" → 多进程下静默失效

| 阶段 | 内容 |
|---|---|
| **现象** | 单进程跑得好好的，一拆进程，群消息一条都不推 |
| **初因** | `GatewayPushService` 只支持 `type=104`，推不了群通知（251）和延迟回执（101），所以作者（我）当时"绕过 gRPC 直接调 `WSSessionManager::pushToUser`" |
| **真因** | 接口能力不足，被迫用共享内存；而共享内存在多进程下是**各自进程的独立副本**，`pushToUser` 永远返回 false，且**不报错** |
| **修法** | 把接口泛化成 `PushFrame(account, type, data)`（+ `PushBatch` 给群扇出），三处调用改走 gRPC |
| **沉淀** | **接口设计要留出"未来要推的东西"的形状**；否则调用方会绕过抽象，债就埋下了。 |
| **加一句**（展示自省） | "最后悔的是当初为了省事绕过 gRPC。绕过的每一处，都在多进程时变成了静默 bug。" |

### 4.4 案例 C：离线补投 60 秒踢线 → 用户永久登不进去

| 阶段 | 内容 |
|---|---|
| **现象** | 极少数用户反复"连接已断开"，重登也没用 |
| **真因** | 补投是"下发一批 → 等这一批全部 ACK → 才推进"，超时 60s 就 `onDisconnect()`。只要有一条消息客户端收到但不会回 ACK（解析失败/校验不过），这一批永远清不空 → 断线 → 重登 → 从 0 重扫 → 撞同一条 → 死循环 |
| **放大效应** | 多网关 + 客户端自动重连后，变成"gw-1 超时 → 重连 gw-2 → 又从 0 扫 → 又超时"，两台网关互相踢皮球 |
| **修法** | 换成"按会话有界同步"：登录时按会话各推最近 20 条（最多 50 个会话），**不等待 ACK**；没 ACK 的下次靠 cursor 重推（客户端去重幂等）；历史由客户端主动拉 |
| **沉淀** | **同步协议不要依赖"对端配合"才能推进**；任何"等 ACK 才前进"的设计都要有"失败也前进"的退路。 |

### 4.5 复盘沉淀的 6 条不变量（可以直接背下来讲）

| # | 不变量 | 如果违反 |
|---|---|---|
| 1 | 只有持有该用户连接的网关才能说"在线" | 消息投到黑洞 |
| 2 | "不在线"必须由**所有**实例都明确否认为准 | 网关不可达被误判为离线 → 消息丢失 |
| 3 | 路由/缓存只影响性能，不影响正确性 | 缓存变成正确性单点 |
| 4 | 一个账号同一时刻至多一个活跃连接 | 双端抢连接、消息投错端 |
| 5 | 非网关进程不得直接访问连接表 | 多进程下静默失效 |
| 6 | 幂等键必须在**写入口**唯一，而不是在消费端去重 | 重复消息、重复计数 |

### 4.6 我也犯过的错（诚实清单，面试很加分）

| 错误 | 后来怎么发现的 | 教训 |
|---|---|---|
| 断言"`queuedWrite` 是唯一抛出源，`start()` 的 catch 兜住它" | 逐个调用点追了一遍可达性，发现那个 throw 实际不可达 | **不要凭"看起来会抛"下结论，要追调用链** |
| 提议"把 7 处错误帧代码抽成一个 `failAndClose`" | 被指出会引入成员变量、布尔参数、掩盖 pre/post-auth 写路径分叉 | **抽象的收益要大于它带来的隐式状态**；允许一点重复 |
| 用 Redis 布尔值当在线判据 | 线上/联调出现"在线收不到" | 见案例 A |
| 补投等 ACK 再推进 | 死循环 | 见案例 C |
| 先按"全量补投"设计 | 用户指出应该按会话有界 + 客户端拉历史 | **先想清楚产品语义，再设计协议** |

### 4.7 如果重做，我会怎么排

1. **先定协议**（type 码表、错误码枚举、幂等键），再写代码——我这次是边写边定，导致 `type=101` 同时表示登录和发消息。
2. **第一天就拆进程**，哪怕部署在同一台机器——这样"能不能跨进程"从第一天就有答案，不会积累"直调内存"的债。
3. **先做可观测**，再做优化——没有 trace，定位"消息卡在哪一段"要花几倍时间。
4. **先写验收再写实现**——我最后才补验收矩阵，回头发现有些设计根本没法验收。

## 5. 高频追问与标准答法

**Q：为什么不用 Go？IM 圈都用 Go。**
> "Go 的 goroutine 和生态确实更适合快速交付，如果团队以迭代速度为先我会选 Go。我选 C++ 是想练协程和手工生命周期管理，而且这个项目确实吃到了无 GC 的好处——万级长连接下延迟更稳。代价是开发慢、库少，我认。"

**Q：为什么 gRPC 不用 brpc？brpc 性能更好。**
> "brpc 单机性能确实更好（bthread），但我们没有成熟的 C++ 服务发现，而 gRPC 的拦截器能直接接 OTel、protobuf 原生、反射方便调试。我的瓶颈不在 RPC 序列化上，所以拿性能换生态是划算的。"

**Q：为什么消息正文放 Mongo，不放 MySQL？**
> "访问模式决定的：消息只追加、按 `{convID, seq}` 范围读。Mongo 的复合索引天然覆盖，而且不需要提前分库分表。MySQL 要做这件事必须先设计分片键，成本前置。"

**Q：为什么 `serverMsgID` 用 UUID 不用 Snowflake？**
> "因为它只需要唯一，不需要有序。UUID 无协调、客户端重试时靠 Mongo 唯一索引 `$setOnInsert` 天然幂等。有序性我放在 `seq` 上，两个 ID 各司其职。"

**Q：你怎么保证消息不丢？**
> "分三段保证：受理靠 MySQL 事务 + `dedupe_key` 唯一键；落库靠 outbox 状态机（`stage`/`state`/租约）可重放；投递靠持久 ACK 回执——没回执就算没送到，登录时按会话 cursor 补。**任何一段失败都不会让消息消失，只会让它晚到。**"

**Q：单网关是单点，你怎么解决？**
> "已经落地了（PR-1～6、PR-8）。三件事：① 每个实例注册到 `/services/GatewayPushService/{instanceId}`，上报的是真实 IP 而不是 `0.0.0.0`；② 登录时写 `gw:user:{account} = instanceId:sessionId`，心跳用 Lua CAS 续期——续期失败说明自己已被顶替，主动断开；③ 推送时按路由表找实例，找不到或调用失败就广播兜底，**所有实例都明确回 false 才算离线**。核心原则是路由只影响性能，正确性由目标网关的返回值保证，所以路由表挂了也不会丢消息，只是多几次 RPC。"

**Q：多网关里最难的是什么？**
> "三个都被我踩过。① **跨实例互踢**：用户先在 gw-1 登录再到 gw-2，gw-1 的连接还活着、还在续期路由，会把路由改回自己——所以续期必须用 CAS，值不匹配就让旧连接自杀。② **路由失效不能变成丢消息**：删掉路由后必须能广播兜底，而且'不在线'只能由所有实例都明确否认为准，否则网关不可达会被误判成离线。③ **升级不能滚动发布**：我删掉了旧的 `PushToUser` 接口，混跑期间旧 PushService 调用会失败、被当成离线、消息被确认成已分发——这一类必须整包替换。"

**Q：这个项目的不足是什么？**
> "三个层面。能力上：撤回、删除、富媒体都只有协议没有实现；群里没有管理员/禁言/公告。架构上：消息走了双轨（单聊 Mongo+Kafka、群聊 MySQL+轮询），两套监控要维护；Mongo 没有 TTL，正文会无界增长。工程上：客户端还没做自动重连（PR-7），这是多网关收益的关键路径；密码还是单轮 SHA-256，没换成 KDF。"

**Q：你的系统瓶颈在哪？**
> "当前瓶颈是单网关的进程内连接表（无法水平扩）和 Mongo 的无界增长（没有 TTL）。前者已经有改造方案，后者需要归档策略。"

**Q：如果 QPS 涨 100 倍怎么办？**
> "按顺序：① 网关水平扩（路由表已设计）；② 消息写入按会话分片（convID 是天然分片键）；③ 会话表读多写多，加 Redis 缓存摘要；④ 归档冷数据。**但我不会提前做**——这些都让系统复杂度上一个台阶，得先有数据证明瓶颈到了。"

## 6. 一页速记（面试前 5 分钟）

**一句话介绍**：C++20 + Boost.Asio 长连接网关 + gRPC 微服务 + MySQL/Mongo/Redis/Kafka/etcd + OTel 全链路的 IM 后端，外加一个 Qt6 客户端。

**选型口诀**：
- 语言：C++ 换性能与可控，付开发效率
- 网络：Beast 换"一个库三件事"（TLS+WS+协程）
- 并发：协程 + strand 换"连接内无锁"
- RPC：gRPC 换生态与拦截器，付异步 API 难度
- 存储：MySQL 存状态、Mongo 存正文、Redis 存路由与令牌（按访问模式拆）
- MQ：Kafka 换"按 convID 分区保序 + 强堆积"
- 注册：etcd 换轻量，自己封 BackbonService 补健康检查
- ID：UUID 给消息、Snowflake 给单聊 seq、自增给群聊 seq、号段给账号

**架构口诀**：网关有状态，服务无状态，异步靠 outbox，送达靠 ACK 回执。

**复盘口诀**：判据要权威、同步不依赖对端、接口要留形状、抽象别带隐式状态。

**三条最能打的细节**（挑一条讲深）：
1. 乱序 ACK 不能用最大水位，否则会永久跳过中间的洞（所以我用持久回执逐条判定）。
2. Kafka 只是投递通道，可靠性在 MySQL outbox + receipts，Kafka 挂了消息不丢。
3. 离线同步改成"按会话有界快照 + 客户端主动拉"，把登录耗时从 O(全部历史) 降到 O(会话数 × 20)。
