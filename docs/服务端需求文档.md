## 1. 产品与系统概述

### 1.1 定位

ape-server 是一套面向桌面/移动 IM 客户端的**长连接即时通信后端**，承担四类职责：

1. **连接接入**：万级并发 WebSocket（WSS）长连接、心跳保活、身份认证、消息分发。
2. **消息可靠性**：单聊消息的「接收 — 持久化 — 投递 — 确认（ACK）」端到端可恢复链路，保证不丢、不重、可补投。
3. **社交关系**：账号注册登录、好友关系与申请、群组与群成员、会话列表与未读数。
4. **基础设施**：微服务注册发现、在线状态、可观测性（Trace/Metric/Log）。

### 1.2 系统边界

**做**：
- 账号体系（11 位手机号注册、10 位数字账号登录、服务端令牌）。
- 单聊（一对一文本消息、历史、已读、离线补投、多端无关的单连接模型）。
- 群聊（建群、入群申请与审批、群成员、群消息、群号）。
- 好友（申请、审批、删除、关系变更通知）。
- 会话（列表、未读、置顶、免打扰、隐藏）。
- 消息与文案的冷热分层存储（Mongo 正文 / MySQL 状态 / Redis 缓存）。

**不做**（当前版本明确不支持，需在协议与产品层面明确告知客户端）：
- 富媒体（图片/语音/视频/文件/位置）的消息收发与存储，仅保留 `contentType` 枚举位。
- 消息撤回、单条删除、按时间物理删除、清空会话正文。
- 群管理员角色、转让群主、群禁言、群公告、群成员名片。
- 好友备注写入、好友黑名单、好友置顶。
- 多端同步（同账号多设备同时在线）、消息漫游以外的端间同步协议。
- 推送通道（APNs/FCM/厂商推送）与离线推送 SDK 集成。

### 1.3 角色

| 角色 | 说明 | 主要能力 |
|---|---|---|
| 未认证连接 | 已建立 WSS 但未通过 `type=101` 认证 | 仅可发送注册（100）、登录（101） |
| 已认证用户 | 持有有效 token 的单聊用户 | 收发单聊消息、拉历史、好友、会话、群 |
| 群主 | `im_groups.owner` | 群审批、改名、踢人、解散 |
| 群成员 | `im_group_members.active=1` | 群消息收发、退群、拉群成员 |
| 网关（内部） | WSS 接入进程 | 认证、协议转换、离线补投、路由 |
| 微服务（内部） | 8 个 gRPC 服务 | 各自领域逻辑 |

### 1.4 典型场景

1. 新用户注册并登录，客户端拿到 token 建立长连接。
2. 建立好友关系后，A 向 B 发单聊消息；B 在线即时收到并 ACK；B 离线则下次登录补投并 ACK。
3. 用户创建群、他人申请加入、群主审批，之后在群内收发消息。
4. 用户删除好友，双方历史消息按删除水位永久不可见，会话被清理。

## 2. 总体架构

### 2.1 进程与部署拓扑

当前实现为**单进程多服务**：一个 `main` 进程内并行运行 8 个 gRPC 服务 + 1 个 WSS 网关 + 1 组 Kafka 生产/消费线程。每个 gRPC 服务由 `BaseServiceServer` 托管，各自占用一个独立 `std::thread`。

| 服务 | 监听 | 职责 | 线程模型 | 注册到 etcd |
|---|---|---|---|---|
| `BackbonService` | 0.0.0.0:50052 | 服务注册发现网关、在线状态查询 | 1 gRPC 线程 | 自身即注册通道 |
| `AuthService` | 0.0.0.0:50051 | 注册、登录、令牌校验 | 1 gRPC 线程 | `Register/Login/ValidateToken` |
| `MsgService` | 0.0.0.0:50053 | 单聊消息受理、历史拉取、outbox worker | 1 gRPC 线程 + 2 worker 协程 | 24 个方法名 |
| `PushService` | 0.0.0.0:50054 | 在线投递、ACK 受理、Kafka 消费 | 1 gRPC 线程 + 4 worker IOC | `PushMsg/DelUserPushToken` |
| `GatewayPushService` | 0.0.0.0:50055 | 供 PushService 反向调用网关推送 | 1 gRPC 线程 | `PushToUser` |
| `GroupService` | 0.0.0.0:50056 | 群域全部逻辑 + 群消息投递协程 | 1 gRPC 线程 + 2s 投递轮询 | `Execute` |
| `FriendService` | 0.0.0.0:50057 | 好友域全部逻辑 | 1 gRPC 线程 | `Execute` |
| `ConversationService` | 0.0.0.0:50058 | 会话列表、已读、设置、隐藏 | 1 gRPC 线程 | 6 个方法名 |
| `WebServer`（网关） | 0.0.0.0:6666 (wss) | TLS/WSS 接入、认证、协议分发、离线补投 | 1 accept 线程 + 4 worker IOC | 不注册 |

**需求 SRV-ARCH-001**：服务端口、etcd 服务名与方法注册清单必须与上表一致；新增服务须同时登记 etcd 与 `main.cpp` 启动序列。
**需求 SRV-ARCH-002**：服务启动顺序为 Backbon → Auth/Msg/Group/Friend/Conversation/GatewayPush → Kafka producer → PushService → OutboxWorker → 各服务 `WaitForEtcdRegistration(30s)` → 网关。任一服务注册超时只告警不阻塞（当前实现）。
**需求 SRV-ARCH-003**（演进）：网关须支持水平扩容；当前 `WSSessionManager` 为进程内单例，多实例时需引入 `user:{account}:gateway` 路由键与跨实例转发（见 §7.3 P1-2）。

| 类别 | 选型 | 说明 |

**需求 SRV-ARCH-004**：所有中间件连接参数必须外置化（配置/环境变量）。当前除 Snowflake 的两个 ID 外全部硬编码，属于必须偿还的技术债（P2-1）。

### 2.3 并发模型

| 组件 | 模型 |
|---|---|
| 网关 accept | 独立单线程 `_acceptor_ioc` |
| 网关业务 | `IOC_Pool` 4 个 `io_context` × 1 线程；每连接 `make_strand` 后 round-robin 绑定，连接内状态**无锁** |
| 网关写 | 每连接一个 `channel<...,shared_ptr<string>>`（容量 256），由 `doDrainWriteQueue` 串行消费，所有写必须走 `queuedWrite` |
| 跨连接共享 | `WSSessionManager` 用 `shared_mutex` |
| gRPC 服务 | 每服务 1 线程 `RunServer()` + 协程化 handler（`BaseServiceServer`） |
| 存储访问 | Redis 4 worker（1 线程 1 连接）；MySQL 2 worker（每 worker 一连接池，写走 pool0 / 读走 pool1）；Mongo 4 worker（每 worker 一连接池） |
| Kafka 消费 | 按 `(topic, partition)` 的 lane 串行处理，lane 内独立 `io_context` 协程 |

**需求 SRV-ARCH-005**：协程 strand 上禁止同步阻塞 IO。当前网关已全面协程化（`docs/gateway_issues.md` 中 P1 已不成立），新增代码须保持。

## 3. 通信协议需求

### 3.1 传输层

| 项 | 需求 |
|---|---|
| 协议 | WSS（TLS 1.2+ over TCP），**二进制帧**，不加密文帧 |
| 端口 | 6666 |
| 握手 | TLS handshake → WebSocket upgrade，两步都成功才可读业务帧 |
| 证书 | `scripts/certs/server.crt` / `server.key`（自签 CA 签发，客户端以 `ca.crt` 做信任锚） |
| 路径 | 当前不校验 URL path、Origin、Sec-WebSocket-Protocol（**需求 SRV-GW-001**：应校验 path 与 Origin 白名单） |
| 帧上限 | 依赖 Beast 默认；**需求**：显式配置 `read_message_max`（建议 1 MiB）并在超限时回错误帧 |

### 3.2 外层信封

所有 WS 帧（双向）均为 protobuf 序列化后的 `sdkws.SdkWSReq` / `sdkws.SdkWSResp` 二进制。

**请求 `sdkws.SdkWSReq`**

| 字段 | 号 | 类型 | 服务端用法 |
|---|---|---|---|
| `requestId` | 1 | string | 原样回传，用于客户端请求-响应关联；缺省时服务端不生成 |
| `token` | 2 | string | 仅认证帧使用；非空时走 token 校验分支 |
| `account` | 3 | uint64 | 认证=登录账号；其余帧被服务端忽略（以连接绑定的账号为准） |
| `deviceID` | 4 | string | 仅回显，不参与索引（**需求 SRV-GW-002**：多端场景必须纳入会话键） |
| `data` | 5 | bytes | 业务载荷，类型由 `type` 决定 |
| `type` | 6 | int32 | 请求类型码，见 §3.3 |
| `trackID` | 7 | int32 | 仅日志 |
| `lastMsgSeq` | 8 | int64 | **当前未使用**（离线补投恒从 0 扫描）；**需求 SRV-GW-003**：应作为增量补投水位 |

**响应 `sdkws.SdkWSResp`**

| 字段 | 号 | 类型 | 服务端填法 |
|---|---|---|---|
| `requestId` | 1 | string | 回显；服务端下推帧（104）为空，离线帧（200）填 `serverMsgID` |
| `token` | 2 | string | 仅认证成功帧回填 |
| `account` | 3 | uint64 | 目标用户账号 |
| `deviceID` | 4 | string | 回显 |
| `errorCode` | 5 | string | 成功为 `""` 或 `"0"`（历史遗留不统一）；见 §3.5 |
| `errorMsg` | 6 | string | 人类可读信息，客户端可直接展示 |
| `data` | 7 | bytes | 业务响应载荷 |
| `type` | 8 | int32 | 必须等于请求 type（`0` 表示心跳/错误） |
| `trackID` | 9 | int32 | 当前未回填 |
| `logID` | 10 | string | 当前未赋值（**需求 SRV-GW-004**：应填服务端 traceId 以便排障） |

### 3.3 请求类型码表（权威定义）

#### A. 认证前（连接首帧，仅允许一次）

| type | 语义 | 请求 data | 响应 type | 响应 data |
|---|---|---|---|---|
| 100 | 注册账号 | `auth.RegisterRequest{phone,nickname,password}` | 0 | 无（仅 `account` 返回新账号） |
| 101 | 登录/认证 | `token` 为空 → data 为**明文密码字节**（非 protobuf）；`token` 非空 → data 忽略，走令牌校验 | 101 | 无（回填 `token`、`deviceID`） |
| 其他 | 不支持 | — | 0 | 无，`errorCode=4401`，随后 `close(4404)` |

#### B. 认证后（消息循环）

| type | 语义 | 请求 data | 响应 type | 响应 data | 状态 |
|---|---|---|---|---|---|
| 0 | 心跳 ping | 无 | 0 | 无，`errorCode=0`、`errorMsg=pong` | ✅ |
| 101 | 发送单聊消息（可批量） | `sdkws.SendMessageReq{msgs[]}` | 101 | `sdkws.SendMessageResp{infos[]}` | ✅ |
| 106 | 统一消息 ACK（在线/离线） | `sdkws.AckReq{serverMsgIDs[],ackType∈{1,2}}` | 无响应 | — | ✅ |
| 220 | 好友：查用户 | `friendpb.Command` | 220 | `friendpb.Reply` | ✅ |
| 221 | 好友：发起申请 | 同上 | 221 | 同上 | ✅ |
| 222 | 好友：好友列表 | 同上 | 222 | 同上 | ✅ |
| 223 | 好友：申请列表 | 同上 | 223 | 同上 | ✅ |
| 224 | 好友：处理申请 | 同上 | 224 | 同上 | ✅ |
| 225 | 好友：删除好友 | 同上 | 225 | 同上 | ✅ |
| 240 | 拉取全部会话 | 无 | 240 | `conversation.GetAllConversationsResp` | ✅ |
| 241 | 会话标记已读 | `conversation.MarkConversationReadReq` | 241 | 无 | ✅ |
| 242 | 更新会话设置（置顶/免打扰） | `conversation.UpdateConversationSettingsReq` | 242 | 无 | ✅ 服务端 |
| 243 | 隐藏会话 | `conversation.DeleteConversationReq` | 243 | 无 | ✅ 服务端 |
| 244 | 拉取单聊历史 | `msg.GetSingleChatHistoryReq` | 244 | `msg.GetSingleChatHistoryResp` | ✅ |
| 250 | 群操作（命令/应答） | `groupchat.Command` | 250 | `groupchat.Reply` | ✅ |
| 102 | 拉取单链 | — | — | — | ⬜ |
| 103 | 拉取混链 | — | — | — | ⬜ |
| 105 | 下推命令消息 | — | — | — | ⬜ |

**需求 SRV-PROTO-001**（P0）：`type=101` 在认证前后语义不同且响应 type 相同，属协议设计缺陷。**应拆分**：登录固定 `type=1`，单聊发送固定 `type=101`，并保证响应 type 与请求一一对应。

**需求 SRV-PROTO-002**（P0）：认证后收到未知 type 时，当前只打 debug 日志、不回帧也不断开（客户端会一直等待）。**必须**回 `errorCode=INVALID_PARAM` 且 `type=0` 的错误帧；连续 3 次未知 type 则断开连接。

#### C. 服务端主动下推

| type | 语义 | data | 触发点 |
|---|---|---|---|
| 104 | 在线消息下推 | `sdkws.MsgData` | `GatewayPushService.PushToUser`（由 PushService 调用） |
| 200 | 离线消息补投（单条） | `sdkws.MsgData`；`requestId=serverMsgID` | 登录成功后 `pullAndPushOfflineMsgs` |
| 209 | 离线补投完成 | 无；`errorCode=0 / SYNC_ERROR` | 补投结束或中途异常 |
| 230 | 好友关系变更通知（无 payload，客户端收到即全量刷新） | 无 | 好友类操作成功后向 `changedAccounts` 中的在线用户推送 |
| 251 | 群变更/新消息通知 | `groupchat.Notice{groupId,lastSeq,messages[],refresh,epoch}` | GroupService 的 `Notify()` 与 `Deliver()` |

### 3.4 幂等与关联

| 场景 | 关联键 | 服务端行为 |
|---|---|---|
| 通用请求-响应 | `requestId` | 原样回显；不维护去重表 |
| 单聊发送 | `clientMsgID` | `im_outbox.dedupe_key = "{sendID}:{clientMsgID}"` 唯一，重复请求返回**首次**的 `serverMsgID/seq`；若 clientMsgID 被复用于不同内容则返回 `INVALID_MESSAGE` |
| 注册 | `x-registration-id` gRPC metadata（由 `requestId` 透传） | `registration_requests` 表按 `request_id` 幂等，重试返回同一账号 |
| 群写操作 | `Command.clientID` | `im_group_requests(actor,client_id)` 保存 hex(payload) 与 reply，重复请求回放上次结果 |
| 群消息 | `(group_id, sender, client_id)` 唯一键 | 重复同内容返回原消息，内容不同返回 `IDEMPOTENCY_CONFLICT` |
| ACK | `(owner_account, server_msg_id)` 主键 | 重复 ACK 幂等 |

**需求 SRV-PROTO-003**：`clientMsgID` 长度 ≤128，字节范围 [33,126]（可打印 ASCII）；`content` ≤ 64 KiB。违者回 `INVALID_MESSAGE`，不得截断。

### 3.5 错误码规范

当前错误码为**字符串字面量**，分散在三层，样式不统一。文档在此定义目标规范，并列出兼容现状。

**目标分层**

| 层 | 表达方式 | 说明 |
|---|---|---|
| WS 传输/协议层 | 数字码 `1`/`401`/`4401`/`500` | 表示协议或链路问题，客户端不应重试业务 |
| 业务域 | 大写下划线字符串 `USER_NOT_FOUND`、`NOT_FRIEND` | 表示业务拒绝，客户端应展示 `errorMsg` |
| gRPC 内部 | gRPC status code | 仅服务间可见，网关翻译为上面两类 |

**必须保持兼容的现有码**

| errorCode | 场景 | 客户端应如何处理 |
|---|---|---|
| `""` / `"0"` | 成功（两值并存，属历史遗留） | 视为成功 |
| `401` | 密码登录失败 | 提示账号或密码错误 |
| `4401` | 首帧 type 不支持 | 视为协议错误，不可重试 |
| `500` | 网关调用 MsgService 异常 | 提示稍后重试 |
| `INVALID_PARAM` | 参数非法（含缺 account、token 无效、载荷解析失败） | 区分：token 无效应回登录页 |
| `PARSE_ERROR` / `IMCOMPLETE_INFO` | 注册帧解析失败/字段缺失 | 提示重新填写 |
| `PHONE_EXISTS` | 手机号已注册 | 提示换号 |
| `ACCOUNT_RANGE_EXHAUSTED` / `ACCOUNT_POOL_UNAVAILABLE` | 账号池耗尽/不可用 | 提示稍后重试 |
| `WRONG_PASSWORD` / `USER_NOT_FOUND` | 登录凭据错误 | 统一提示「账号或密码错误」 |
| `NOT_FRIEND` | 发送对象非好友（好友关系已删） | 提示关系已解除 |
| `INVALID_MESSAGE` | 消息字段非法/clientMsgID 冲突 | 提示重新输入 |
| `PENDING` | 消息已受理但尚未落库确认 | **保持 pending，等待 101 补发响应** |
| `SYNC_ERROR` | 离线补投失败 | 提示重新登录重试 |
| `HISTORY_ERROR` / `CONVERSATION_ERROR` / `SERVICE_UNAVAILABLE` / `DB_ERROR` | 下游不可用 | 提示稍后重试 |
| `ALREADY_FRIEND` / `ALREADY_HANDLED` / `APPLICATION_NOT_FOUND` / `FORBIDDEN` / `INVALID_TARGET` | 好友域业务拒绝 | 展示 `errorMsg` |
| `GROUP_NOT_FOUND` / `GROUP_DISMISSED` / `NOT_MEMBER` / `OWNER_REQUIRED` / `OWNER_CANNOT_LEAVE` / `ALREADY_JOINED` / `INVALID_NAME` / `NAME_UNCHANGED` / `EMPTY_MESSAGE` / `INVALID_SEQ` / `MEMBERSHIP_CHANGED` / `IDEMPOTENCY_CONFLICT` / `GROUP_NUMBER_EXHAUSTED` / `INVALID_REQUEST_ID` / `APPLICATION_HANDLED` / `CACHE_ERROR` | 群域业务拒绝 | 展示 `errorMsg` |
| `UPGRADE_REQUIRED` | 用 type=101 发群消息 | 客户端必须改用 type=250 |

**需求 SRV-PROTO-004**（P0）：统一定义错误码枚举（proto `enum ErrorCode`），停止新数字码；`INVALID_PARAM` 必须拆分为 `MISSING_ACCOUNT` / `TOKEN_INVALID` / `BAD_PAYLOAD` 三个码（当前客户端无法区分「该重新登录」还是「该改参数」）。

### 3.6 心跳与超时

| 项 | 要求 |
|---|---|
| 心跳方向 | 客户端主动 ping（`type=0`），服务端回 `pong` |
| 心跳间隔 | 建议 30s（客户端实现值）；服务端不强制 |
| 在线状态 TTL | `user:{account}:online` = 300s，由每次心跳续期 |
| 离线补投 ACK 等待 | 60s/批，超时断开连接（保留数据库回执，重登可续） |
| gRPC deadline | 认证 15s；好友/会话 8s；群 10s；历史 10s；ACK 8s；**`SendMessages` 当前无 deadline（需补 10s）** |
| `SendMessages` 等待落库 | 最长 8s，200ms 轮询 outbox；超时返回 `PENDING` |
| Outbox 租约 | 45s；重试退避 `min(60s, 1s << attempts)` |
| Kafka 投递确认 | 12s（50ms 轮询） |

**需求 SRV-PROTO-005**：服务端**必须**实现主动心跳探测（服务端 ping / 空闲超时踢线）。当前仅靠客户端 ping，客户端静默断网时在线状态最长滞留 300s。

### 3.7 协议演进约束

**需求 SRV-PROTO-006**：
1. proto 文件为唯一契约源，客户端仓库须同步 `proto/` 并重新生成。
2. 字段只增不改号；废弃字段保留 `reserved`。
3. `sdkws.SdkWSResp` 预留 `logID` 作为排障锚点，必须回填。
4. 新增 WS type 必须在本文件 §3.3 登记并给出客户端最低版本要求。

## 4. 功能需求

### 4.1 接入网关（GW）

#### SRV-GW-010 连接建立
- 接受 TCP → TLS handshake → WebSocket upgrade；两步失败均记录错误并关闭。
- 连接绑定到某个 worker 的 strand，之后所有读写与状态访问都在该 strand 内。

**实现状态**：✅

#### SRV-GW-011 首帧认证分发
- 首帧必须是 `type ∈ {100,101}`；否则回 `4401` 并 `close(4404)`。
- 认证成功后：绑定 `account_` → 注册到 `WSSessionManager` → 启动写队列 → 写在线状态 → 回成功帧 → 起消息循环 → 执行离线补投。

**实现状态**：✅

#### SRV-GW-012 连接注册表
- 键为 `account`（10 位账号），**每账号仅保留一个 session**，后登录覆盖前者。
- `registerSession` 覆盖时必须主动关闭旧连接并通知其客户端「已在别处登录」。

**实现状态**：🟡 —— 覆盖逻辑存在，但**不关闭旧连接**，旧连接陷入「既收不到推送又不知道自己已被顶替」的状态（P0-3）。

#### SRV-GW-013 写队列
- 所有出站帧统一入 `channel`（容量 256），由单一 drain 协程串行 `async_write`，避免 Beast `soft_mutex` 断言。
- 入队失败（队列满/已断开）视为连接不可用，**关闭连接**，由客户端重登恢复。

**实现状态**：✅

#### SRV-GW-014 离线消息补投
- 数据源**唯一**为 MongoDB（`GetMsgsBySeqFromMongoAsync`），Redis 不参与分页拼装。
- 批大小 50；游标从 0 开始；每批下发后等待 ACK（60s 超时）。
- 每条下发前须过 `WithFriendMessage(..., requireUndelivered=true)`：好友关系成立、`seq > deleted_seq`、outbox 已提交、且无 ACK 回执。
- 补投结束发 `209`；异常发 `209 + SYNC_ERROR`。

**实现状态**：✅（缺 `lastMsgSeq` 增量优化，每次全量扫描，P1-4）

#### SRV-GW-015 ACK 处理
- `AckReq.ackType` 仅接受 1（在线）/2（离线），其他值静默丢弃。
- 逐条调用 `PushService.AckMsg`，最多 2 次尝试、间隔 200ms；两次失败则关闭底层 socket。
- **需求**：改为批量 ACK（`AckBatch`），避免 N 条 = N 次 gRPC（P0-6）；`AckMsgReq.seq` 必须回填。

**实现状态**：🟡

#### SRV-GW-016 断线清理
- 幂等；顺序：置 `disconnected_` → 取消 ACK 定时器 → 清 pending → 关写队列 channel → `cancel/shutdown/close` 底层 socket → 若仍为活跃 session 则 `unregister` 并把在线状态置 `"0"`（TTL 300s）。
- 不得与在途 `async_write` 并发发起 WebSocket close 帧。

**实现状态**：✅（离线 key 用 `setex 300 "0"`，非 `del`；接受 5 分钟滞后）

#### SRV-GW-017 优雅停机
- 收到 SIGINT/SIGTERM：关闭 acceptor → 停止接收新连接 → 等待在途 session 自然关闭（带 deadline）→ 停止 IOC 池 → 停止各服务 → 刷 OTel。
- **当前**：`stopPool()` 先 `work_guard.reset()` 再 `io_context.stop()`，丢弃 pending handler。

**实现状态**：🟡（P1-3）

### 4.2 认证服务（AUTH）

#### SRV-AUTH-001 注册
| 项 | 规则 |
|---|---|
| 入口 | WS `type=100` |
| 校验 | `phone` 非空；`nickname` 非空；`password` 非空 |
| 服务端校验 | `requestId` 非空且 ≤64 且 `[A-Za-z0-9-]`；`phone` 11 位且 `^1[3-9]\d{9}$`；`nickname` ≤256；`password` ≤1024 |
| 账号分配 | 从 `account_pool` 取 10 位账号（区间 1000000000–9999999999，低水位 1000 触发补 10000 个） |
| 幂等 | `registration_requests.request_id` 同一请求 ID 返回同一账号 |
| 落库 | `users(user_id, account, nickname, phone, password_hash, password_salt, ...)` + `registration_requests` 同事务 |
| 响应 | `type=0`、`account=新账号`；**不签发 token、不进入认证态** |

**实现状态**：✅

#### SRV-AUTH-002 登录
| 项 | 规则 |
|---|---|
| 入口 | WS `type=101` 且 `token` 为空，`data` = 明文密码 |
| 校验 | `account != 0`、`password` 非空 |
| 凭据比对 | `SHA-256(salt ‖ password)` 与 `users.password_hash` 等值比较 |
| 成功 | 生成 token，写 Redis，更新 `last_login_at` |
| 失败 | `401` + `errorMsg="login failed: <reason>"`，随后关闭连接 |
| 响应 | `type=101`，回填 `token`、`deviceID` |

**实现状态**：✅（密码哈希强度不足，见 SRV-SEC-003）

#### SRV-AUTH-003 令牌
| 项 | 要求 |
|---|---|
| 格式 | 随机 UUID v4 字符串（36 字符，含连字符）；**非 JWT** |
| 存储 | Redis `token:{token}` = `"{userID},{account}"` |
| TTL | 7 天（604800s） |
| 校验 | `ValidateToken(token)` → `{valid, userID, account, expiresAt}`，且 `account` 必须等于请求 account |
| 续期 | **需求**：每次成功校验延长 TTL（滑动过期）；当前不续期 |
| 吊销 | **需求**：提供登出/踢下线接口（`RevokeToken`）；当前无 |

**实现状态**：🟡

#### SRV-AUTH-004 账号池
- `account_pool` 预生成账号（`status 0=可用/1=已分配`），`account_pool_cursor` 记录号段游标，`account_pool_refill_lock` 实现 DB 级补货锁。
- 若池空：先尝试补货，仍失败回 `ACCOUNT_POOL_UNAVAILABLE`（可同请求 ID 重试）。

**实现状态**：✅

### 4.3 好友服务（FRIEND）

单入口 `FriendService.Execute(Command) → Reply`，按 `Command.operation` 派发；网关把 WS `type 220..225` 映射为 `operation = type - 220`，并**强制覆写 `actor` 为连接账号**。

| operation | WS type | 语义 | 关键规则 | 状态 |
|---|---|---|---|---|
| `LookupUser` 0 | 220 | 按账号查公开信息 | `target != 0`；返回 `PublicUserInfo{userID,nickname}` | ✅ |
| `Apply` 1 | 221 | 发起好友申请 | 不能加自己；目标必须存在；已是好友 → `ALREADY_FRIEND`；已有同向 pending → **复用该申请不重复插入**；`message` ≤512 | ✅ |
| `ListFriends` 2 | 222 | 好友列表 | `limit` clamp(1,100)；首页固定 `snapshot=MAX(id)`，后续 `id > after AND id <= snapshot`；`limit+1` 判 `hasMore` | ✅ |
| `ListApplications` 3 | 223 | 申请列表（收+发双向） | 同上分页；不过滤状态 | ✅ |
| `HandleApplication` 4 | 224 | 同意/拒绝 | 仅 `recipient` 可处理（否则 `FORBIDDEN`）；`accept` → `Accepted`，否则 `Rejected`；已是同一终态幂等成功；状态冲突 → `ALREADY_HANDLED` | ✅ |
| `DeleteFriend` 5 | 225 | 删除好友 | 双向删 `friends` 两行；双方各写 `friend_chat_deletions(owner,peer,deleted_time,deleted_seq=Snowflake)`；把双向 pending 申请置 `Rejected`；硬删双方 `im_conversations` 该会话行；排 `im_outbox(operation=2)` 清理历史正文；返回 `clearedConversations` | ✅ |

**跨域规则（重要）**

- **好友关系判定**：`friends` 必须存在 `(A,B)` 与 `(B,A)` **两行**，`COUNT(*) == 2` 才算好友。
- **删除水位**：任何消息可见性判定都要求 `seq > friend_chat_deletions.deleted_seq`；关系恢复后旧消息**依然不可见**（设计如此）。
- **并发控制**：所有写操作先 `lockPair(low,high)`，对 `friend_pairs` 主键行做 `INSERT ... ON DUPLICATE KEY UPDATE` 取排他行锁，隔离级别 READ COMMITTED。
- **变更通知**：操作成功后网关向 `Reply.changedAccounts` 中的在线用户推 `type=230`（无 payload，客户端收到即全量刷新）；不在线者跳过，靠登录后 `ListFriends` 全量同步。

**实现状态**：✅（缺：黑名单、备注写入、好友上限、申请频控、反向 pending 去重，见 §7.2）

### 4.4 群组服务（GROUP）

单入口 `GroupService.Execute(Command) → Reply`；网关固定 WS `type=250`，`operation` 由客户端指定，`actor` 强制覆写。群域使用**独立的消息体系**（MySQL 存储、群内连续 seq），不经过 Kafka / Mongo / PushService。

| operation | 值 | 语义 | 权限与规则 | 状态 |
|---|---|---|---|---|
| `List` 0 | 我加入的群 | `im_groups ⋈ im_group_members`，按群 id 游标分页，`limit` clamp(1,100) | ✅（未过滤 `dismissed`） |
| `Create` 1 | 建群 | 群名非空 ≤256 字节；群 id=Snowflake；分配 10 位群号；插群主成员行；`member_count=1` | ✅ |
| `Search` 2 | 按群号/群 id 查群 | 10 位群号按 `im_group_numbers`；≤10 位输入未命中 → `GROUP_NOT_FOUND` | ✅ |
| `Apply` 3 | 申请入群 | 非成员、群未解散；写 `im_group_applications(status=0)`，`reason=Command.text` ≤512 | ✅ |
| `Applications` 4 | 待审申请 | **仅群主** | ✅ |
| `Review` 5 | 审批 | **仅群主**；同意 → upsert 成员（`active=1`，`epoch=IF(active=0,epoch+1,epoch)`）并重算 `member_count` | ✅ |
| `Members` 6 | 成员列表 | 需为成员；`Member.owner` 由 `account==groups.owner` 现算；按 account 游标分页 | ✅ |
| `Rename` 7 | 改名 | **仅群主**；新名非空 ≤256 且不等于旧名 | ✅ |
| `Leave` 8 | 退群 | 任意成员；**群主禁止**（`OWNER_CANNOT_LEAVE`）；`active=0` + 重算人数；重复退群幂等成功 | ✅ |
| `Kick` 9 | 踢人 | **仅群主**；目标不能是群主；`active=0` + 重算人数 | ✅ |
| `Dismiss` 10 | 解散 | **仅群主**；`dismissed=1`；未处理申请置 `status=3`；群主重复解散幂等成功 | ✅ |
| `Send` 11 | 发群消息 | 需为成员；正文非空 ≤65536 字节；`seq = last_seq + 1`（群行 `FOR UPDATE` 内）；`(group,sender,client_id)` 唯一幂等 | ✅ |
| `Pull` 12 | 拉群消息 | 需为成员；`after = max(Command.after, join_seq)`，`snapshot = min(Command.snapshot, last_seq)`，`limit` clamp(1,50) | ✅ |
| `Ack` 13 | 投递确认 | 需为成员；`after <= last_seq`；写 `ack_seq = GREATEST(ack_seq, max(after, join_seq))` | ✅ |
| `Read` 14 | 已读 | 需为成员；写 `read_seq`；未读由 `COUNT(seq > max(join_seq, read_seq) AND sender <> actor)` 实时算 | ✅ |
| `MyApplications` 15 | 我的入群申请 | join `im_group_numbers` 带群号 | ✅ |

**群消息投递**

- 小群（`member_count <= 200`）：`type=251 Notice` 内联最近 20 条 `seq > ack_seq` 的消息。
- 大群（`> 200`）：`Notice.refresh=true`，客户端必须自行 `Pull`。
- 后台 `Deliver()` 每 2s 轮询在线成员，对 `last_seq > ack_seq` 的群在事务内构造 Notice 并**同步入队在提交前**完成（保证不丢）。

**群成员身份令牌 `epoch`**

- 成员行 `epoch` 在「重新入群」时 +1；客户端每次请求带 `Command.epoch`，与库中不一致 → `MEMBERSHIP_CHANGED`，客户端须刷新群资料。
- `Notice.epoch` 回传，客户端据此丢弃过期通知。

**实现状态**：✅（缺管理员角色、禁言、公告、转让群主、入群验证三态、成员上限，见 §7.2）

### 4.6 消息服务（MSG）

#### 4.6.1 发送链路（单聊，端到端）

```
客户端 type=101
  → 网关（覆写 sendID、建 OTel root span）
  → MsgService.SendMessages
      ├─ 校验字段，重写 convID/serverMsgID/seq/sendTime（服务端权威）
      ├─ MySQLHandler.QueueSingleMessage  （单事务：lockPair → 好友校验 → 删除水位 → 幂等查/插 im_outbox）
      └─ 200ms 轮询 GetOutboxTask，最长 8s
            ├─ stage>=1 → 成功回填 MsgData
            ├─ state==3 → NOT_FRIEND
            └─ 超时 → PENDING（后续由 outbox worker 补发 101 响应）
  → OutboxWorker（2 协程）
      ├─ stage 0→1：Mongo 存正文(committed=false) + RecordConversationMessage + stage=1
      └─ 发布：Mongo PublishMessage(committed=true) → 无 ACK 则写 Redis msg:{id} + Kafka(msg_topic, key=convID)
                → state=0, available_at=now+5s（等 ACK）
  → PushService（消费 msg_topic）
      ├─ Redis 取正文，miss 则回源 Mongo
      ├─ MessageDispatchDone 幂等检查（outbox.dispatch_done / receipts）
      ├─ WithFriendMessage 二次校验 + 查 user:{recvID}:online
      ├─ 在线 → GatewayPushService.PushToUser → 网关 type=104
      └─ 离线 → 保留在 Mongo，等下次登录补投
  → 客户端 ACK type=106 → PushService.AckMsg → 写 im_message_receipts + 排 outbox(operation=3)
  → OutboxWorker：Mongo status=2 + 清 Redis 缓存
```

**服务端权威字段**

| 字段 | 生成规则 | 说明 |
|---|---|---|
| `convID` | `to_string(min(sendID,recvID)) + "_" + to_string(max(...))` | 单聊会话 ID = 「小号_大号」 |
| `serverMsgID` | UUID v4 字符串（36 字符） | 全局唯一，Mongo unique 索引 |
| `seq` | **Snowflake ID**（全局单调、时间有序、会话内不连续） | 会话内最大 seq 存 `im_conversations.max_seq`（`GREATEST` 推进） |
| `sendTime` | 服务端毫秒时间戳 | 覆盖客户端时间 |
| `sendID` | 网关强制覆写为连接账号 | 防伪造 |

#### 4.6.4 Outbox 状态机

`im_outbox` 是**数据库驱动的可靠投递状态机**，用于把「消息受理」与「消息落库 + 投递」解耦。

| 字段 | 语义 |
|---|---|
| `operation` | 1=单聊发送；2=好友删除后历史清理；3=ACK 后清理 |
| `dedupe_key` | operation=1：`"{sendID}:{clientMsgID}"`（唯一键）；op=3：`"{owner}:{serverMsgID}"`；op=2：`"{convID}:{cutoff}"` |
| `state` | 0 待执行 / 1 已领取 / 2 完成 / 3 取消 |
| `stage` | 0 正文未提交 / 1 Mongo 已存且会话已更新 |
| `dispatch_done` | Kafka 分发是否已完成 |
| `attempts` / `available_at` / `lease_until` / `lease_token` | 重试与租约控制 |

**状态迁移要求**

1. `state=0` 且 `available_at<=now`，或 `state=1` 且 `lease_until<=now` → 可领取（`FOR UPDATE SKIP LOCKED`），置 `state=1, lease_until=now+45s, lease_token=uuid`。
2. `persist` 阶段（仅 op=1，`stage=0`）：好友失效 → `state=3`；否则 Mongo 存正文 + 会话 upsert → `stage=1`。
3. 发布阶段：`PublishMessage` → 无 ACK 则 Redis 缓存 + Kafka 投递 → `state=0, available_at=now+5s`；有 ACK 则 `state=2`。
4. 失败：`RetryOutboxTask` 指数退避（`min(60s, 1s<<attempts)`），`attempts++`，仅当 `lease_token` 匹配才更新。
5. 成功：`state=2`，并给发送者补发 `type=101` 响应（`requestId=clientMsgID`）。

**实现状态**：✅

#### 4.6.5 群消息

**实现状态**：✅（设计上是有意的双轨，但带来了两套消息模型，见 §7.2）

### 4.7 推送服务（PUSH）

#### SRV-PUSH-001 在线投递

| 步骤 | 规则 |
|---|---|
| 1 | 群消息 → `UNIMPLEMENTED "Use GroupService Execute for group messages"` |
| 2 | 从 Redis `msg:{serverMsgID}` 取正文，miss 回源 Mongo；都没有则跳过 |
| 3 | `MessageDispatchDone(recvID, serverMsgID)` 为真则跳过（幂等） |
| 4 | `WithFriendMessage(msg, action, requireUndelivered=true)`：好友双向成立、`seq > deleted_seq`、outbox `stage>=1 && state!=3`、无 ACK 回执 |
| 5 | 查 `user:{recvID}:online`；**Redis 异常必须上抛**（不得当离线处理） |
| 6 | 在线 → `GatewayPushService.PushToUser(recvID, MsgData bytes, convID)`；`false` 视为未送达，保留离线恢复 |
| 7 | 成功 → `ConfirmMessageDispatch(serverMsgID)` 置 `state=2, dispatch_done=1` |

**实现状态**：✅

**语义边界（需求约束）**：`PushToUser.success=true` 仅表示「已入队到目标连接」，**不代表客户端已收到**。可靠性完全由「未收到 ACK 就不置 `state=2`」保证。

#### SRV-PUSH-002 ACK 受理

```
AckMsg(owner, serverMsgID) → 校验 owner 与 recipient 一致 → 
  查 im_outbox：state=3 直接成功；stage=0 → "Message has not been committed"；
  outbox 无 payload 时回源 Mongo 取正文；群消息 → UNIMPLEMENTED；
  事务内：INSERT im_message_receipts ON DUPLICATE KEY UPDATE + 
          INSERT im_outbox(operation=3) ON DUPLICATE KEY UPDATE id=id
```

**实现状态**：✅（不等待 Redis/Mongo 清理完成，清理由 worker 异步执行）

**需求 SRV-PUSH-003**：`AddPendingOfflineAck` 已废弃（返回 `UNIMPLEMENTED`），应从 proto 中移除或标注 `reserved`；`pending_ack:*` 系列 Redis key 只剩删除逻辑，应彻底清理。

| Mongo 不可用 | 消息受理仍成功（进 outbox），投递延后；历史拉取明确报错 |
| MySQL 不可用 | 所有写操作失败并回 `DB_ERROR`，不得部分成功 |
| Kafka 不可用 | outbox 保持 `state=0` 重试；消息不丢 |
| 下游服务不可用 | 网关回 `SERVICE_UNAVAILABLE`/`CONVERSATION_ERROR`/`HISTORY_ERROR`，连接保持 |
| 进程重启 | 未 ACK 消息靠 Mongo + receipts 补投；outbox 靠租约过期回收 |
| 网关重启 | 客户端必须能重连（当前客户端无自动重连，见客户端文档） |

**需求 SRV-REL-001**：任一下游调用必须带 deadline（当前 `SendMessages` 缺失）。
**需求 SRV-REL-002**：服务启动失败必须返回非 0 退出码（当前证书加载失败被 `catch` 吞掉并 `return 0`，运维无法感知）。

### 7.2 需求缺口（按优先级）

**P0（阻塞上线）**

1. **协议语义冲突**：`type=101` 双重语义 + 未知 type 黑洞（SRV-PROTO-001/002）。
2. **同账号重复登录不踢旧连接**，旧连接陷入僵尸态（SRV-GW-012）。
3. **撤回/删除消息全部为 stub**，客户端却已有对应 UI 与协议位（SRV-MSG-002）。
4. **错误码不可判别**：`INVALID_PARAM` 一词多义，客户端无法决定「重新登录」还是「改参数」（SRV-PROTO-004）。
5. **无速率限制**，单连接可无限刷消息与好友申请（SRV-PERF-001）。
6. **批量 ACK 缺失**，N 条消息 = N 次 gRPC（SRV-GW-015）。
7. **密码哈希强度不足**（SRV-SEC-003）。

**P1（扩容前必须）**

1. 网关优雅停机（丢弃 pending handler）。
2. 多实例 Session 路由（`user:{id}:gateway` + 跨实例转发）。
3. 方法级服务路由替代硬编码地址。
4. `lastMsgSeq` 增量补投，避免每次全量扫描 Mongo。
5. `min_seq`/清空会话语义（`ConversationService.ClearUserConversationMsg`）。
6. 混链拉取（会话列表首屏）。
7. `SdkWSResp.logID` 回填 traceId。
8. 服务启动失败非 0 退出码。

**P2（技术债）**

1. 中间件连接参数外置化。
2. 删除遗留 Redis key 与 `AddPendingOfflineAck`。
3. 社交三域业务逻辑从 `MySQLHandler` 抽出到 Repository。
4. 清理 `docker/mysql/init.sql` 的遗留表。
5. `im_groups` 索引与 `Search` 的 `FOR UPDATE` 去锁。
6. 服务端自身容器化。
7. `offline_msg_topic` 删除。
